= Module 1: The Environment
:navtitle: Module 1: The Environment

*Duration:* 10 minutes

This module orients you to the pre-deployed environment. Everything described here is already running — your job is to click through each console and confirm you can reach it before starting the hands-on modules.

== Your Company: Acme Inc.

You are a platform engineer at Acme Inc., a financial services company. Your team manages three Java applications:

[cols="2,1,3",options="header"]
|===
| Application | Risk | Description
| `wire-transfer-svc` | *High* | Customer-facing wire transfer processing service. Subject to PCI-DSS and SOX compliance. Downtime or security incidents have direct business impact.
| `benefits-mgmt-app` | *Low* | Internal employee benefits enrollment application. Used by HR during enrollment periods. Not customer-facing; brief downtime is tolerable.
| `report-generator-app` | *Low* | Internal scheduled report generation service. Runs batch jobs for compliance and analytics. No real-time availability requirements.
|===

All three applications are stored in your GitLab instance under the `acme-{guid}` group. Each has intentionally outdated dependencies with known CVEs — that is the point.

== The Platform Components

Open each of the following in a new browser tab. You will use all of them during the lab.

=== Lightwell Network (Simulated)

The Lightwell Network publishes remediated, signed builds of open source components — the `.rhlw-NNNNN` versions you read about in Module 0. In a production environment, these would be fetched from `packages.redhat.com` with an active Lightwell subscription.

For this lab, a *simulated* Lightwell repository is hosted in your tenant's Nexus instance at:

----
https://nexus-lightwell-nexus-{guid}.{openshift_cluster_ingress_domain}/repository/lightwell-java-remediated
----

This contains the same artifact structure as the real Lightwell repository — Maven metadata, POMs, and JARs with `.rhlw` version suffixes — so the automation behaves identically.

Your Nexus also serves as a Maven build cache and an OCI container registry. Tekton pipelines push built container images to Nexus, and ArgoCD deploys from there.

=== GitLab

Your three applications are in the `acme-{guid}` group:

* URL: `https://gitlab-gitlab.{openshift_cluster_ingress_domain}`
* Username: `{user}`
* Password: `{password}`

Browse to the `acme-{guid}` group and confirm you can see all three repositories. Each has a `pom.xml` with vulnerable dependencies and a `renovate.json` that configures the Lightwell preset.

=== Renovate Operator

Renovate is a dependency update tool that creates merge requests when it finds newer versions. The Renovate operator is installed at the cluster level and can run scans on demand via `RenovateJob` custom resources.

The operator web UI is at:

----
https://renovate-operator-renovate-operator.{openshift_cluster_ingress_domain}
----

You will create a `RenovateJob` in Module 2.

=== Tekton Pipelines (CI)

Tekton handles the build side: compiling the application, generating an SBOM, signing the container image, and pushing it to the registry. Pipelines trigger automatically when a merge request is merged in GitLab.

You can observe pipeline runs in the OpenShift Console under *Pipelines*.

=== ArgoCD (CD)

ArgoCD handles the deployment side: when a new container image is available, ArgoCD detects the change and rolls it out.

* URL: `https://openshift-gitops-server-openshift-gitops.{openshift_cluster_ingress_domain}`
* Log in with *Log in via OpenShift* using your OpenShift credentials.

NOTE: In this lab, ArgoCD deploys straight to production. Real-world customers typically configure ArgoCD with multiple stages — test, staging, production — each with its own sync policy and approval gate.

=== Trusted Profile Analyzer (TPA)

Each tenant has its own TPA instance, so you only see SBOMs and vulnerability data for your own applications. TPA stores and queries the SBOMs generated by your builds. In Path 1 (Renovate), you will use it after the build to compare SBOMs and confirm the fix landed. In Path 2 (AI), TPA plays an active role — the orchestrator queries it to find which applications are affected by a CVE.

* URL: `https://tpa-{guid}.{openshift_cluster_ingress_domain}`
* Log in via SSO with your credentials.

=== ServiceNow (Simulated)

A lightweight mock of ServiceNow's ITSM interface. In Path 2, the Ansible Orchestrator opens a ticket when a remediation starts and updates it at each stage — TPA analysis, AI assessment, MR creation, build, deploy, and closure.

* URL: `https://snow-mock-snow-{guid}.{openshift_cluster_ingress_domain}`

You do not need to interact with ServiceNow in Path 1.

=== Ansible Automation Platform and Orchestrator

The Ansible Orchestrator drives the full automation workflow in Path 2. It receives events from Nexus, dispatches queries to TPA, hands off to AI agents, and tracks the entire flow.

* Orchestrator URL: `https://ao.{openshift_cluster_ingress_domain}`
* Username: `{user}`
* Password: `{password}`

You do not need to interact with the Orchestrator in Path 1.
