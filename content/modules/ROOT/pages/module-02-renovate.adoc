= Module 2: Quick Win — Deterministic Remediation with Renovate
:navtitle: Module 2: Renovate (Path 1)

[WARNING]
====
This module is a *work in progress*. Steps and screenshots may change before the final version.
====

*Duration:* 25 minutes

This module walks through *Path 1* — the simplest way to automate Lightwell remediations. No AI, no orchestration. https://docs.renovatebot.com/[Renovate^] watches the Lightwell mirror in Nexus for new `.rhlw` versions and creates merge requests to bump your dependencies. Standard CI/CD handles the build and deploy.

In this lab you will remediate a single app — *report-generator-app* — but in the real world Renovate can manage dozens or hundreds of repositories simultaneously. Enterprises commonly configure it to:

* Auto-merge patch-level updates for low-risk internal services
* Group related dependency bumps into a single merge request
* Schedule scans during off-hours to avoid disrupting development
* Apply different policies per repository or dependency type (e.g. auto-merge test dependencies, require review for production frameworks)

For this workshop we are *not* enabling auto-merge, so you can inspect every result without Renovate acting on its own. See the https://docs.renovatebot.com/[Renovate documentation^] for the full set of configuration options.

== Understanding Renovate and the Lightwell Preset

The key integration point is the *java-remediated* preset from `lightwell-experience/renovate-config`. This preset:

* Disables the standard Maven manager (so Renovate does not propose random upstream bumps)
* Adds a custom regex manager that reads `pom.xml` and looks up versions in the Lightwell repository
* Uses a versioning scheme that only bumps the `.rhlw-NNNNN` suffix — keeping the upstream version the same

Open https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] (username: `{user}`, password: `{password}`). Navigate to the `acme-{guid}/report-generator-app` repository and open `renovate.json`. You will see it extends the Lightwell preset:

[source,json,role=copypaste]
----
{
  "extends": ["github>lightwell-experience/renovate-config:java-remediated"]
}
----

The preset defaults to `packages.redhat.com` (the real Lightwell registry), but since we are using a simulated Lightwell repository in Nexus, the RenovateJob you create next will supply your dedicated Nexus URL and credentials at runtime — keeping them out of the source repository.

== Creating the RenovateJob

The Renovate operator is already installed on the cluster. A `renovate-runner` service account and its credentials are provisioned in your namespace. Create a `RenovateJob` custom resource to tell the operator what to scan — run the following command in the terminal on the right:

[source,yaml,role=execute,subs=attributes+]
----
cat <<'EOF' | sed "s/{guid}/{guid}/g" | oc apply -f -
apiVersion: renovate-operator.mogenius.com/v1alpha1
kind: RenovateJob
metadata:
  name: renovate-{guid}
  namespace: {user}-renovate
spec:
  schedule: "*/5 * * * *"
  parallelism: 1
  secretRef: renovate-token
  serviceAccount:
    name: renovate-runner
  provider:
    name: gitlab
    endpoint: https://gitlab-gitlab.{openshift_cluster_ingress_domain}/api/v4
  discoveryFilters:
    - "acme-{guid}/report-generator-app"
  image: ghcr.io/renovatebot/renovate:44.145.1
  access:
    adminUsers:
      - "{user}@demo.redhat.com"
  renovateConfig:
    fileName: config.json
    inline: |
      {
        "onboarding": false,
        "requireConfig": "optional",
        "branchConcurrentLimit": 0,
        "prConcurrentLimit": 0,
        "prHourlyLimit": 0,
        "commitMessagePrefix": "[Lightwell]",
        "commitMessageExtra": "({{{newVersion}}})",
        "hostRules": [
          {
            "matchHost": "nexus-lightwell-nexus-{guid}.{openshift_cluster_ingress_domain}",
            "hostType": "maven",
            "username": "admin",
            "password": "{password}"
          }
        ],
        "packageRules": [
          {
            "matchManagers": ["custom.regex"],
            "matchDatasources": ["maven"],
            "registryUrls": ["https://nexus-lightwell-nexus-{guid}.{openshift_cluster_ingress_domain}/repository/maven-public"]
          },
          {
            "matchPackageNames": ["com.acme.*:*"],
            "enabled": false
          }
        ],
        "dockerfile": { "enabled": false },
        "github-actions": { "enabled": false }
      }
EOF
----

Here is what the key fields do:

* *schedule* — scan every 5 minutes (you can also trigger runs on demand from the web UI)
* *secretRef* — GitLab personal access token for the `renovate-bot` user (pre-provisioned)
* *provider* — connects to your dedicated GitLab instance. The operator also supports `github`, `bitbucket-server`, `gitea`, and other providers — the RenovateJob spec is the same, just change the `provider.name` and `endpoint`.
* *discoveryFilters* — scopes Renovate to only scan `report-generator-app`. In production you would list all repositories, use wildcards (e.g. `acme-*/*`), or omit this field entirely to scan every repository the bot user can access.
* *access.adminUsers* — restricts visibility in the Renovate web UI to your user only
* *renovateConfig* — inline Renovate config that merges with (and overrides) the `renovate.json` in each repository. Key settings:
** `hostRules` — credentials for your Nexus Maven registry. In this lab the password is inline for simplicity; in production you would store credentials in a secrets manager such as HashiCorp Vault or use the External Secrets Operator to sync them into Kubernetes Secrets, then reference them via environment variables using Renovate's https://docs.renovatebot.com/self-hosted-configuration/#detecthostrulesfromenv[`detectHostRulesFromEnv`^] feature
** `packageRules` — points the Lightwell custom manager at your `maven-public` group and disables scanning of internal `com.acme.*` packages
** `dockerfile` / `github-actions` — disabled for this lab. Renovate supports https://docs.renovatebot.com/modules/manager/[over 100 package ecosystems^] including npm, pip, Go modules, Helm charts, Terraform providers, and container images. You enable or disable each manager independently — for example, `"npm": { "enabled": true }` would add JavaScript dependency scanning alongside the Java Lightwell preset. You can also configure https://docs.renovatebot.com/configuration-options/#automerge[auto-merge^] for low-risk dependency classes (e.g. test-only updates, patch-level bumps) so they land without human review.

NOTE: Under the hood, the Renovate operator manages Kubernetes `RenovateJob` and `RenovateProject` custom resources. You can inspect them with `oc get renovatejobs` and `oc get renovateprojects`. In a production environment, these resources would typically be managed by ArgoCD alongside your other GitOps-managed infrastructure.

== A New Lightwell Remediation Becomes Available

Now simulate a new Lightwell remediation arriving. The xref:attachment$inject-remediation.sh[inject-remediation.sh] script uploads a remediated version of a dependency into your Nexus `lightwell-remediated` repository — the same thing the Lightwell Network does in production.

Run the following command in the terminal on the right to inject a remediated build of Netflix Hystrix (one of the vulnerable dependencies in `report-generator-app`):

[source,bash, role=execute]
----
bash /showroom/repo/content/modules/ROOT/attachments/inject-remediation.sh \
  org.springframework.cloud:spring-cloud-starter-netflix-hystrix:2.2.10.RELEASE \
  rhlw-00001 \
  "Netflix Hystrix"
----

The script discovers your Nexus instance automatically, creates a minimal POM and JAR with the `.rhlw-00001` version suffix, and uploads them alongside Maven metadata. You should see output like this:

== Watching Renovate React

Return to the https://renovate-operator-renovate-operator.{openshift_cluster_ingress_domain}[Renovate web UI^] and click *Trigger* or *Trigger All* to force an immediate run. Once the execution starts, click *Logs* to watch it in real time. This time you will see Renovate:

. Discover your repository
. Scan `pom.xml` and extract all dependencies
. Query Nexus for each dependency via the `maven-public` group
. Find `spring-cloud-starter-netflix-hystrix` has a new version: `2.2.10.RELEASE.rhlw-00001`
. Create a merge request in GitLab

Once the run completes, the UI updates to show the created merge request with the `[Lightwell]` prefix in the title.

== Reviewing and Approving the MR

Switch to https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^]. Navigate to the `acme-{guid}/report-generator-app` repository, then click *Merge requests* on the left. You should see a new merge request from `Renovate Bot` with the `[Lightwell]` prefix in the title.

image::gitlab-renovate-mr.png[Merge requests from Renovate Bot in GitLab]

Open the `[Lightwell]` merge request and inspect the diff. You will see a single change in `pom.xml`:

[source,diff]
----
-        <version>2.2.10.RELEASE</version>
+        <version>2.2.10.RELEASE.rhlw-00001</version>
----

This is the Lightwell pattern: the upstream version stays the same (`2.2.10.RELEASE`), and the `.rhlw-00001` suffix indicates this is a remediated rebuild that preserves API compatibility.

Approve and merge the request.

== Watching the Pipeline

Merging the MR triggers a Tekton pipeline run. Switch to the OpenShift Console and navigate to *Pipelines* in the `build-{guid}` namespace.

image::pipeline-run-renovate.png[Tekton pipeline building the remediated app]

Watch the pipeline:

. *Clone* — fetches the updated source from GitLab
. *Build* — compiles the application with the remediated dependency
. *Generate SBOM* — produces a CycloneDX SBOM for the new build
. *Sign* — signs the container image using Trusted Artifact Signer
. *Push* — pushes the signed image to the registry

At this point, the application is remediated and the new container image is built, signed, and ready to go into production.

== Summary

You have just completed the *Quick Win* path:

. A remediated artifact arrived in Nexus
. Renovate detected the new `.rhlw` version and created a merge request
. You reviewed and approved the change
. Tekton built and signed the patched application with a SLSA Level 3 compliant software supply chain
. The remediated application was rolled out into production (in a real environment, this would progress through dev, test, and staging first)
. TPA confirms the vulnerability is resolved via SBOM comparison

This is the lowest-effort way to start automating Lightwell remediations — no AI, no orchestration, no ticket management. And because the pipeline uses Tekton Chains for signing and attestation, every build meets SLSA Level 3 compliance out of the box.

=== Tradeoffs

The Quick Win path works well for a handful of applications and a manageable volume of remediations. But it has limits:

* *Scale* — when Lightwell publishes dozens or hundreds of remediations per week across your portfolio, the merge request volume becomes unmanageable for human reviewers.
* *Context* — Renovate creates merge requests mechanically. It does not assess business risk, check whether the affected application is customer-facing or internal, or correlate with your ITSM system.
* *Auto-merge helps, but only so far* — Renovate's maintainers https://docs.renovatebot.com/key-concepts/automerge/[recommend automerging^] for updates where you would click "merge" anyway: lock file maintenance, dev-only dependencies, patch-level bumps with good test coverage. But for production frameworks, compliance-sensitive services, or anything without strong test coverage, human review remains essential — and at scale, that review needs context that Renovate alone cannot provide.

For organizations that need to handle volume, assess risk, and maintain an audit trail, the next module introduces the *Full Automation* path — where Ansible Orchestrator, AI agents, and ITSM (IT Service Management) systems work together to triage, assess, and route remediations based on business context.
