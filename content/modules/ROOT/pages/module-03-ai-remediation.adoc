= Module 3: Full Automation — AI-Assisted Remediation
:navtitle: Module 3: Full Automation

*Duration:* 30 minutes

include::partial$lab-access.adoc[]

Module 2 ended with a deliberate limitation: Renovate found one dependency in one repository and asked you to merge it. That works until the day Lightwell publishes forty remediations across sixty repositories, and "ask a human to merge it" stops being a strategy.

This module walks through the same remediation event, handled by services running on your OpenShift cluster instead of by you. The platform opens a Snow incident, asks Trusted Profile Analyzer which applications are actually affected, applies each application's own approval policy, and dispatches an AI agent to write the merge request. The pipeline then tests the change and writes the results back into the merge request body, so that when a human *is* asked to decide, they are reading evidence rather than guessing.

You will remediate two of your three applications:

* `benefits-mgmt-app` — internal HR application, risk class `LOW`, policy `auto_approve`. The platform merges it without you.
* `wire-transfer-svc` — payment-critical and PCI-scoped, risk class `HIGH`, policy `needs_approval`. The platform does everything *except* the last step, and then waits for you.

The difference is the approval policy. Automation handles the low-risk change end to end; the high-risk change stops and waits for your review.

== Foundations

Three ideas run through this module:

* *Evidence before decision* — the pipeline fills in the validation table before anything is allowed to merge. The business benefit is faster, more defensible reviews: a reviewer reads measured results instead of gathering evidence by hand.
* *Risk-based approvals* — `benefits-mgmt-app` merges automatically; `wire-transfer-svc` waits for a person. The business benefit is focus: reviewer time goes to high-risk changes, and low-risk fixes ship without waiting in a review queue.
* *Verify the artifact, not the dashboard* — the SBOM contents are the fact; vulnerability counts depend on what the scanner knows. The business benefit is accurate reporting: teams avoid both false confidence and unnecessary escalations.

Everything in this flow runs on OpenShift: the artifact manager, GitLab, Trusted Profile Analyzer, the event and workflow services, the AI agent, the Tekton pipelines, Argo CD, and the Acme applications themselves.

[cols="1,2,2",options="header"]
|===
| Stage | Quick Win (Module 2) | Full Automation (this module)

| Trigger
| Renovate polls the artifact manager on a schedule
| The artifact manager fires a `component CREATED` webhook as soon as the artifact is published

| Who finds the affected apps
| Renovate reads one repository's `pom.xml`
| TPA is queried for every SBOM containing the component

| Who writes the fix
| Renovate's regex manager
| The `impact-analyzer` AI agent (OpenCode)

| What the merge request says
| A one-line version bump
| CVE, CVSS, risk class, and a validation table filled in by the pipeline

| Who approves
| Always you
| Per-app policy — `auto_approve` or `needs_approval`

| Audit trail
| Git history only
| A Snow incident, commented at every stage

| Build, sign, deploy
| Shared — Tekton, OCI registry, Argo CD, TPA
| Same tools and same steps
|===

Both paths use the same build, sign, and deploy steps. Full automation changes who decides what to change and who approves it.

== How the Pipeline Is Organized

Every service in this flow runs on OpenShift, and each does the job it is best at. Event-Driven Ansible listens for the `.rhlw` artifact event and starts the workflow. Ansible Orchestrator coordinates the stages, while TPA, GitLab, OpenCode, Tekton, and Argo CD handle analysis, source control, the fix, builds, and deployment. Each stage runs and is recorded as it completes.

Your project contains *three* workflows, not one, and the split is the first thing worth understanding:

[cols="1,3",options="header"]
|===
| Workflow | Runs when

| *Lightwell Remediation — Start*
| A remediated artifact is published. Ends when the merge requests are ready.

| *— Merged*
| A merge request is merged — by you or by automation. Follows the build through.

| *— Deploy*
| Argo CD reports the application healthy. Closes the incident out.
|===

They are separate so that each workflow can be re-used in different contexts — for example, the Merged workflow runs the same way whether a person or the automation merges the request. Each stage is a short execution started by a webhook. The Snow incident ties the stages back into one story.

== Two Applications, Two Policies

Each application repository carries a `.lightwell/policy.json` file. It is the primary control that decides whether a human is interrupted — but it is not the only one. If any step in the merge request pipeline fails (unit tests, regression scan, license compliance), the merge is blocked regardless of policy, and the change requires human review:

[cols="2,1,1,3",options="header"]
|===
| Application | Remediation Owner | Approval Policy | `riskClass` and why

| `wire-transfer-svc`
| `ao`
| `needs_approval`
| `HIGH` — payment-critical, PCI-scoped system

| `benefits-mgmt-app`
| `ao`
| `auto_approve`
| `LOW` — internal HR application, no regulated data

| `report-generator-app`
| `renovate`
| —
| `LOW` — internal reporting tool, no regulated data
|===

For this workshop, the policy travels with the code, in the repository, reviewed like any other change. In practice, other, external policy engines could be used to evaluate whether a change is allowed to merge. The workflow does not care where the policy comes from, only that it is machine-readable and can be evaluated.

TIP: Open `.lightwell/policy.json` in `acme-{guid}/wire-transfer-svc` in https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] before you start. It is a single JSON object with four fields, and it is the entire governance model for this lab.

== Watch the Validation Checks Run

The merge request is created before any testing has happened, so every check row in the *Automated Validation* table starts as `Pending` (yours might be all "green" already if you waited long enough.) A Tekton pipeline, `build-pull-request`, runs against the open merge request, executes `mvn verify` together with the CycloneDX SBOM plugin, and then rewrites that one section of the description with real results.

. Scroll to the bottom of the merge request. For the next minute or two, you should see the widget below:
+
image::m3-mr-merge-blocked.png["The merge request widget showing a running pipeline and Merge blocked: Pipeline must succeed",link=_images/m3-mr-merge-blocked.png,window=_images]
+
*Merge blocked: 1 check failed — Pipeline must succeed.* Nothing has gone wrong. The pipeline is still running, and GitLab will not let anyone merge — you, a colleague, or the automation — until it reports success. The wording is unfortunate: "1 check failed" here means "the required check has not passed yet", not "a test broke".

. Click the *Pipeline #<n>* link. You should see one stage, named *external*, running `Pipelines as Code CI / build-pull-request`.
+
image::m3-gitlab-pipeline-running.png["The GitLab pipeline page showing a single external stage running Pipelines as Code CI / build-pull-request",link=_images/m3-gitlab-pipeline-running.png,window=_images]
+
"External" means it is an external (to GitLab) pipeline, in this case a Tekton Pipeline running on OpenShift. There is no `.gitlab-ci.yml` in this repository and no GitLab runner involved. Tekton is mirroring its status back here so that GitLab has something to gate on.

. To see the actual pipeline, switch to the *OpenShift Console* tab, navigate to *Pipelines* → *Pipelines* → *PipelineRuns*, and select the `build-{guid}` project.
. Open the running `build-pull-request` PipelineRun. Confirm you can see these four tasks:
+
.. `fetch-source` — clones the merge request branch
.. `run-tests` — `mvn verify` plus the CycloneDX SBOM, against the *remediated* dependency
.. `baseline-tests` — the same tests again against the dependency version you are replacing. This is what makes *Regression scan* a comparison rather than an assumption, and it is why the pipeline takes roughly twice as long as a plain build
.. `report-validation` — writes the results into the merge request, and fails the pipeline if any check row is not green
+
image::m3-tekton-pipelinerun.png["The PipelineRun details view in the OpenShift console showing fetch-source, run-tests, baseline-tests and report-validation",link=_images/m3-tekton-pipelinerun.png,window=_images]
+
That last task is the one holding your Merge button. Once it passes, the gate opens.

. Return to the GitLab merge request and refresh it. The table should now have filled in. Confirm you can find each row and understand what it measures:
+
[cols="2,3",options="header"]
|===
| Check | What it actually measures

| Acme Inc. Risk Class
| The `riskClass` from the application's policy file — a classification, not a measured check

| Binary signature verification
| An *integrity* check — the published JAR is compared against the checksum the artifact manager recorded for it. The lab mirror ships no detached GPG signature, so this is not a cryptographic signature check and is labelled accordingly.

| SBOM integrity
| A CycloneDX SBOM is generated in the same build and asserted to list the new remediation version (the bumped _coordinate_, e.g. `org.apache.commons:commons-text:1.9.rhlw-00001`) and the CVE that triggered it

| Unit tests
| `surefire` results from `mvn verify`

| Integration tests
| `failsafe` results from the same run

| Dependency compatibility
| Asserts that what the `pom.xml` declares is what the build actually resolved

| Regression scan
| Re-runs the whole suite against the target branch's `pom.xml` and compares the result test by test, so a test that was already failing before the bump is not blamed on it

| License compliance
| Compares the license declared by the base POM against the remediated POM, normalized so that equivalent phrasings do not raise a false alarm
|===

image::m3-mr-validation-filled.png["The same table after build-pull-request has run, with every check Passed",link=_images/m3-mr-validation-filled.png,window=_images]

IMPORTANT: Every one of those check rows is measured. Nothing is ever reported green without having been measured, which is the only reason the table is worth putting in front of a reviewer at all — and a row that *could not* be established says so, rather than quietly reading `Passed`.

The regression scan is why this pipeline takes about twice as long as you might expect: it builds the application a second time against the dependency version you are replacing, so that "no behavioral change" is a comparison rather than an assumption. Roughly ninety seconds in total.

.. *Pipeline #60 passed* on `update-artifact-1.9…` — the branch build finished and every row of the table went green. Only now is merging possible at all.

.. *Pipeline #61 passed* on `main` — merging started a second, different build: the one that produces the image you will deploy.

. Check the timestamps while you are there. The merge happened roughly two minutes after the request was opened, not seconds — the automation was waiting for `build-pull-request` to report before it merged. It could not have jumped that queue even if it had tried.

This is the scale case. An internal HR application, a compatible rebuild, and every automated check green — there is no decision that needs a person. At forty remediations a week, the saving is not the merge click; it is the review time and context switching around it.

[NOTE]
====
The decision is made from `.lightwell/policy.json` in the application's own repository, and it fails closed. If that file is missing, unreadable or malformed, the workflow treats the application as `needs_approval` and routes it to a human. Nothing merges itself by accident.
====

+
.. The incident was raised the moment the artifact manager announced the artifact — before anything was known about who was affected
.. Child tickets were opened, one per application TPA said was genuinely affected
.. Each application reached a reviewable merge request
.. Merge, build and deploy were each noted as they landed
.. The parent moved to *Resolved* once Argo CD reported the application Healthy

. Open a child. Confirm it carries the per-application detail: the merge request link, the CVE, the verifier outcome, the pipeline run, the Argo CD application and the route the fixed code is now serving on. The parent tells an operator where things stand; the child tells them what happened.

The incident is marked _Resolved_ when the app is deployed, not when it is merged or shows a green pipeline. The `SNOW finalize` step only runs in the Deploy workflow, so the ticket stays open until the remediated code is running. A build that passes but never ships does not close anything.

That is also why three workflows rather than one long-running job. The Start run ends when the merge requests are ready; merge and deploy arrive later as webhooks and start their own short executions. The incident is what stitches them back into a single story — which is precisely the job a ticket is supposed to do.

[NOTE]
====
For a risk or compliance audience, this is the key point: the incident was open before the change existed, accumulated every decision and measurement as the work happened, and closed when the fix was live.
====

== Summary

You have just run the *Full Automation* path end to end:

. You published a remediated artifact; the artifact manager raised a `component CREATED` event
. The artifact event started the remediation workflow in Ansible
. The workflow opened a Snow incident ticket before proposing any change
. TPA answered which applications were genuinely affected, from SBOM data
. Each application was classified against its own `.lightwell/policy.json`
. The `impact-analyzer` agent opened a merge request carrying CVE data, risk class and a validation table
. The `build-pull-request` pipeline tested the change and wrote the real results back into that table
. `benefits-mgmt-app` was auto-approved and merged automatically, without you
. `wire-transfer-svc` passed every check, and its merge request still said human review was required, so it waited for you to merge it in GitLab
. Both were built, signed, promoted and deployed by the same pipeline and Argo CD
. The parent incident resolved once Argo CD reported the deployment Healthy, carrying a complete, timestamped trail

=== Key Takeaways

Compared with the quick win path, there are important differences:

* *Scope* — the system knows which applications contain the component, because it asked TPA rather than scanning a single repository.
* *Evidence* — by the time a human looks at the change, the tests have run and the results are in the merge request. The reviewer reads measurements, not promises.
* *Proportionality* — attention is spent where it changes the outcome. An internal HR application merges itself. A PCI-scoped payment service does not, and no amount of green ticks changes that.

Scale is what makes this necessary. One remediation a week is a Renovate problem. Forty a week across sixty repositories, each needing a risk decision and an audit trail, is an orchestration problem — and the human can only stay in the loop if low-risk changes like `benefits-mgmt-app` stop asking for review.
